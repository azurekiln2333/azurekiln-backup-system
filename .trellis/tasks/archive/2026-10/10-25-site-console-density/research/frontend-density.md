# Frontend information density research

Inspected on 2026-10-25. Planning only: recommendations below are not implementation approval or measured before/after results. Only this research document was changed; no product code, preview, build or test suite was run.

## Confirmed requirement update

The user has chosen multiple repositories per site and an optional site note. The site title and access address must appear on the **same line**, including mobile. A site can retain multiple saved addresses, but its list row displays **the first saved address only**. The visible link label is the **hostname/domain only**, while navigation retains the complete safe URL including scheme, port, path and query. For example, `https://panel.example.com:8443/admin` displays `panel.example.com` and still opens the complete URL. Keep the full ordered address list in the editor and do not rotate addresses, select one randomly or discard the rest. All-page versus sites/overview-only density remains an open product choice.

## Why the current site page feels sparse

- `web/src/components/SitesView.vue:100` renders each site as four vertically separated blocks: identity/counts/update time, addresses, tags, then linked jobs. `web/src/style.css:329` gives the row 18px vertical padding and 12px gaps. It consumes a full-width row even when each field is short, leaving unused space to the right. Metadata repeats counts directly above the actual address/task lists.
- Linked jobs are another layer of bordered boxes (`style.css:344`); at <=620px every `.site-job` becomes full width (`style.css:646`). Two related jobs therefore add separate visual rows. Actual task names/types/status and the many-to-many mapping are useful content and must remain visible; replacing them with a count would manufacture density by losing information.
- The toolbar also wraps search, tag filter, association filter and totals (`SitesView.vue:75`). A row-height goal alone cannot prevent an oversized heading/toolbar from wasting the first screen.
- The issue is primarily spacing and distribution, not large body text: site names are already 13px, task names 12px, addresses 11px and metadata/tags 10px (`style.css:334-350`). Keep these readable sizes; do not shrink them to meet a height target.

## Why addresses resemble tags

`style.css:316` makes tags small filled rounded chips with primary-color text and 3px/7px padding. `.site-domain` uses the same padding, small radius and primary text, with another filled surface (`style.css:338`). Global anchors have no underline (`style.css:81`), and address anchors contain only text (`SitesView.vue:120`). Their link behavior is hidden behind a classification-like shape.

Proposed distinction:

- Addresses: one transparent hostname/domain text link beside the site title, with a small external-link/globe affordance, clear hover/focus underline and existing safe HTTP(S) href handling. Derive the hostname label from the shared parsed/normalized URL; do not merely truncate the full URL or remove the port/path from the stored value or href. The title/address identity line does not wrap into separate lines. Very long hostnames may ellipsize within a real nonzero-width area, with the full selected URL available through its accessible link name, focus/hover disclosure and editor; native hover-only `title` must not be the only way to read it. Invalid legacy values remain readable nonlinks using their original text as fallback, with wrapping/disclosure in the editor and constrained readable text in the row; do not invent a safe-looking hostname or clickable href from invalid data.
- Tags: retain the filled chip/button grammar and active filter state. Do not make the entire tag/address area a single indistinguishable badge collection.
- Repository links: a strip of small provider-icon links with accessible provider/repository names, visible focus and direct navigation. Multiple repositories, including two on the same provider, need distinct repository labels rather than four fixed provider toggles. Their icon/link treatment should group with navigation, not tag filters. Preserve navigation when an icon is unavailable. Allow a large repository strip to wrap in its own metadata area instead of pushing the selected address off the title line or hiding configured links.

## Proposed structure and spacing

Desktop site rows should distribute an identity area and linked job names/status across columns, with actions at the edge. The identity area's first line is always **site title + one selected address**; the address is no longer an independent column or vertical block. Place short tags and the repository-icon strip on a compact secondary line, or alongside the identity line only when both title and address retain useful width. Secondary count/update metadata can move into an inline subdued line or detail, rather than requiring an additional block. This retains the actual site-to-job mapping and frees horizontal space without smaller text.

At narrow widths, reserve the full available content width for the nonwrapping title/address identity line and move action buttons or repository icons to a following metadata line when needed. Both title and selected hostname need a readable text fragment and nonzero width; an external-link icon alone, an ellipsis alone or a tooltip-only address does not satisfy the request. Constrain these two text areas with `min-width: 0` and deliberate truncation only for unusually long hostnames, preserve full accessible title/URL values and provide disclosure usable with keyboard/touch as well as a mouse. The row must stay inside the viewport. Missing addresses use a short nonlink placeholder in the same identity position; they must not borrow a repository URL. The ordinary list label omits protocol, port, path, query and fragment; these remain intact in the safe navigation URL and editor.

Other meaningful groups may stack and wrap. Avoid mandatory full-width boxes for each short linked job when compact name/status links can fit. Do not hide task names, set zero-width columns, or clip entire groups to pass a density check. A site with many repositories or jobs may legitimately be taller than the standard fixture; additional saved addresses alone do not add list-row height because only one is displayed.

The optional note is free text, not a classification chip or URL. Keep full note editing and reading in the editor (and a detail surface if that is part of the final design). A muted single-line list preview is a proposal: show it only when nonempty, give it a note affordance or label, and make the full value available without a mouse. Do not reserve an empty note row. A long note should not silently make every list row a paragraph; the final plan must choose between a disclosed/truncated preview and editor/detail-only notes. This preview choice remains a presentation recommendation, not a confirmed requirement.

For `SiteEditor.vue:147`, every field is currently full width despite the two-column form primitive. The repeated name/address preview at line 181, long helper paragraphs and 19px/20px field gaps make the dialog tall before repository and note fields are added. Proposed design work should combine concise help with the relevant label, use two columns only for genuinely short independent fields, and remove or collapse the redundant preview. Retain every saved full address, explain that the first address's hostname is displayed in the list, and preserve address order through editing. Repository editing must support multiple entries, including different repositories on the same provider, and optional notes need a clearly labeled multiline input. Keep inline errors, search, shared-job indicators, unresolved-task warnings, save state and draft preservation. Do not force the long address/repository/association inputs into narrow columns for appearance alone.

The following are **project proposals**, not copied reference values: desktop main inset 16px; heading 18-20px with 12px bottom gap; panel heading 44-48px with 10-12px/16px padding; common panel gaps 12-16px; table cell vertical padding 8-10px; form gaps 12px; modal body padding 16-20px. Preserve current body/label font sizes and adequate mobile control targets (proposed minimum 36px for primary controls).

## Proposed measurable acceptance

Agree these targets with the final scope before implementation. **<=104px desktop and <=156px mobile are suggested maximum standard-site row heights for this project; neither is a new-api original value or a current measured result.**

- Revise the standard populated fixture to at least eight sites: a 4-8-character site title, **two saved full addresses with only the first hostname displayed beside the title** (include a URL with port/path, such as the confirmed example), two short tags, two linked jobs with actual names/status, **two repository links** and **one short nonempty note**. At least one job must be shared by two sites, and one site should have two repositories on the same provider. This measures the expanded requirements rather than the earlier one-repository/no-note case. Add separate long-title/hostname/note/many-repository fixtures and missing/legacy-invalid/unloaded/error/unlinked cases. If notes are editor/detail-only in the approved design, note presence must not create list spacing.
- At 1440x900, show at least six complete standard site rows before first-page scroll, with standard row height <=104px. Measure the actual first-row offset and final visible row, so a large title/toolbar cannot consume the gain. Record before/after visible complete rows using the same data and viewport.
- At 390x844 and 360x780, show at least three complete standard site rows, with standard row height <=156px and no horizontal document scroll. Long/many-link cases may grow naturally; never enforce the target with whole-row fixed-height clipping, task-name line clamps or hidden task names. An explicitly approved note preview or exceptionally long hostname may use disclosed truncation as described above.
- Every site title, selected hostname and linked task name has nonzero visible geometry in both themes at all four existing widths. Assert title and selected-hostname text occupy the same identity line, exactly one address is displayed for a multi-address site, the first saved address is selected, and all full addresses remain available after opening/reloading the editor. Assert the port/path fixture's label is exactly `panel.example.com` while its href still includes `:8443/admin`; accessibility/disclosure exposes the full URL. Long title/hostname cases must expose readable fragments and full values without horizontal overflow. Invalid legacy values remain nonlinks and readable, without unsafe href generation. Preserve full linked-task names, shared task labels under every associated site and real loading/unresolved semantics. Existing visibility assertions are a floor, not a density measurement.
- Address anchors are visibly links with transparent treatment and focus indication; tags remain distinct filtering buttons. Repository icon controls expose provider/repository names to assistive technology and have working navigation independent of the icon asset.
- If all-page spacing is approved, add bounded representative table-row/control/panel geometry on jobs/runs/files/settings and inspect the seven-page, four-width, two-theme matrix. A passing screenshot count alone is not sufficient evidence of higher density.

Retain protections against missing title/selected-address/task text and extend them with visible-complete-row, same-line alignment, exactly-one-address and height checks. Its current requirement that every saved domain appears in a row must deliberately change to the selected-address contract plus full editor preservation; this is a confirmed product change, not permission to hide the selected address with CSS.

The same script pins desktop main padding to `20px 24px 28px 24px` at line351, overview stat padding to `18px 20px` at line474, overview metric count to four at line470, overview columns to 1.6:1 at line468, and direct panel table inset to >=19px at line574. A shared spacing/overview redesign requires approved replacement contracts; do not just delete failing assertions. Continue to guard aligned grid tops, scroll containment, actual text, shell geometry, one h1, theme behavior and mobile actions.

Open product choice for parent: all-page compact primitives or sites/overview first. Multiple repositories, optional notes, first-saved-address selection, hostname-only visible label and complete safe navigation URL are confirmed; note-preview presentation remains a recommendation. Exact overview contents still need convergence with the parallel overview research before the editor and row layout are finalized.
