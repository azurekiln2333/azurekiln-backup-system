# Single-file jobs and server-side task cloning

Source-only research, 2026-10-25. This investigation changed no product code. Anchors refer to the inspected source before the concurrent Herdr implementation; line numbers may move. Subsequent implementation decisions in the task design supersede historical options below. The separately authorized `tests/file-clone.test.mjs` now covers the selected contracts; its non-integration run passed with 10 passes and two explicit skips.

## Confirmed direction from the parent

- Add `type: 'file'`, reuse `sourcePath`, support manual/scheduled full backups. Watching stays directory-only. File jobs do not expose exclusions and save `excludes: []`.
- Clone with `POST /api/jobs/:id/clone`, optional request name, server-side preservation of configuration/secrets and all site associations. New clone is paused; preserve schedule/watch configuration without activating it. System task cloning returns 409; an active non-system source can be cloned.
- New clone has a fresh task identity, timestamps, no last run/next run/baseline/history/archive ownership. Existing tasks/sites/runs/archives remain intact.

## Single-file contract and exact backend seams

1. **Shared schema:** add `'file'` to `jobSchema.type` at `shared/contracts.mjs:117`. Keep `sourcePath` as the existing absolute source input, and keep the current archive/destination/retention/retry/notification settings. No new SQL table or file-specific credential fields are needed. `newJob(type)` at `:233` already delegates to this schema.
2. **Path validation:** extend `resolveSourcePath` (`server/config.mjs:56`) with an explicit regular-file selector, e.g. `{file: true}`. Keep `{directory: true}` behavior unchanged and never request both. After the existing path/root/symlink checks, require `lstatSync(real).isFile()` or throw `400 SOURCE_NOT_FILE`. A directory, FIFO/socket/device or link must not qualify. Retain `allowMissing` only for already-authorized missing-source flows such as pausing; normal create/enable/execution requires the file.
3. **Existing security boundary:** preserve absolute/NUL checks (`config.mjs:57`), root containment and state isolation (`:59`), each-component symlink rejection (`:61`), canonical containment (`:76`) and lexical plus resolved DATA_DIR/SOURCE_ROOTS isolation (`:28`, `:51`). Do not bypass these with raw `copyFile(req.body.sourcePath, ...)`. Recheck the source at execution and immediately before opening it; save-time checks alone do not protect later runs.
4. **Save validation:** add an explicit file branch to `validateJob` (`server/app.mjs:22`) before the Vaultwarden fallback at `:32`: `resolveSourcePath(config, job.sourcePath, {file:true,allowMissing})`; normalize `job.excludes=[]`. Existing watch rejection at `:24` already enforces directory-only. Existing destination/password/cron/timezone checks stay shared. Without this branch a file job falls into Vaultwarden validation.
5. **Execution preflight:** `execute` currently forces every non-system source to be a directory (`server/backup.mjs:504`) and traverses it with `validateTree` (`:508`). Branch file source resolution to `{file:true}` and size accounting to its file stat. Keep full/incremental directory logic (`:506`) unchanged. A **zero-byte regular file is valid**; do not reuse the database-export nonempty check (`:348`). The existing temp/disk quota checks (`:482`, `:528`) still apply.
6. **Preparation:** add `prepareFile` or an equally narrow file branch before the final `tarDirectory` fallback (`server/backup.mjs:572`). Never tar the parent directory as `.`: that would include siblings and change the requested scope. All prepared output belongs under the existing run-owned `payload`/stage (`:477`). The final compression, archive verification, hashes, upload, retention, downloads and cleanup (`:573` onward) are reusable.

### Payload alternatives and selected restore behavior

The implementation selected the existing **one-member inner tar** convention (`file.<stamp>.tar` containing `./<basename>`), retaining file metadata; the staged-files/manifest option below is historical research, not a requested new format. Tests must extract the actual selected tar payload rather than require an extra manifest.

- Use `payload/files/<original basename>` plus a small fixed `manifest.json` describing kind/version, original basename, relative payload path, copied byte count and SHA-256; record mtime/mode if their restore semantics are implemented. Separating `files/` avoids collisions with a source named `manifest.json` or `RESTORE.md`. Do not store an absolute source path as an extraction member or generate executable restore commands from arbitrary filename text.
- Stage by a bounded streaming copy from an opened regular-file handle to a newly created owned output, with the run abort signal. This works with the existing sampled quota monitor (`backup.mjs:495`) and avoids a whole-file memory buffer; bare `copyFile` cannot consume that signal. Reuse `fileHashes` (`:56`) for the copied bytes. This is a content backup, not an online database snapshot; existing database adapters keep their specialized snapshot guarantees.
- For source replacement races: preserve current component validation, open without following the final link where the platform supports it, verify the opened handle is a regular file, and compare handle identity with the revalidated selected path before streaming. If using a simpler path-based copy, do not claim the preflight lstat eliminates a later symlink swap. A source replaced by a link must not cause bytes outside SOURCE_ROOTS to enter the archive. Optional before/after size/mtime checks can fail a changing source rather than claim a consistent point-in-time snapshot.
- The minimal restore promise is extraction into a fresh user-chosen directory and exact filename/bytes/hash verification. Reuse outer 7z/ZIP/tar.gz handling (`backup.mjs:590`, `:612`); do not add automatic writes back to the original source path. A local `RESTORE.md` may explain the payload and optional mode/mtime restoration, but must not imply an application restore endpoint exists. Avoid promising ownership/ACL preservation from a plain staged copy.
- An alternative that matches directory payload convention is a one-member inner tar using `-C <parent> -- <basename>`; never omit `--` before user-controlled basenames. It needs equivalent source revalidation/identity protection and extraction assertions. The staged `files/` payload is the smaller implementation for one file.

### Compatibility and frontend handoff

- Existing persisted types/defaults and directory archives remain unchanged. Jobs/runs stay JSON in the existing SQLite tables (`server/store.mjs:44`, `:245`); whole-state backup/restore carries the new type without an archive-format change. Older archives remain readable by the updated application. An older application binary does not understand the new `file` type; do not describe restoring new file jobs into old binaries as supported.
- `GET /api/sources` already emits ordinary files (`server/app.mjs:273`, `:279`); no new browsing endpoint is necessary. `PathPicker.vue:23` filters them out and `:81` only selects a directory, so the frontend needs an explicit file-selection mode. `FileManagerView.vue:131` currently exposes the backup action only for directories.

## Server-side cloning: recommended contract

`POST /api/jobs/:id/clone` accepts no body or `{name?: string}`. Validate with a narrow object schema; optional name follows the current trimmed 1–100-character name rule. When omitted, choose a clear bounded copy name, e.g. original name plus a copy suffix truncated to the schema limit. Do not let callers supply identity/runtime fields, raw secret flags, destination overrides or arbitrary full job objects through this endpoint. Return **201** and the ordinary public Job DTO.

### Clone sequence and transaction

1. Route resolves the original with `store.getJob(id,{includeSecrets:true})` (`server/store.mjs:158`); reject missing source and the built-in/system type before copying. Public job DTOs remove archive/Vaultwarden/new-api passwords and expose `passwordSet` only (`:95`), so a browser-side repost of a DTO cannot preserve the actual secrets.
2. Project only configuration through `jobSchema.parse(original)` and apply the bounded new name plus `enabled:false`. This strips `id`, timestamps, `lastRun`, `nextRunAt`, configured flags and other runtime-only properties. Preserve archive settings/password, database credentials, description/tags, source, destinations, schedule/watch settings, retention/retry/notifications. Apply `validateJob(...,{allowMissing:true})` to the paused clone as selected in the design addendum: temporarily missing allowed sources can be retained, while extant wrong-type/forbidden/symlink sources still reject. Ordinary create/enable/execution retain normal required-source checks.
3. Recommended store primitive: **`cloneJob(sourceId, validatedInput)`**, owned by the store and implemented inside existing `inTransaction` (`server/store.mjs:133`). Check source existence/protection, call `saveJob(validatedInput)` **without an id**, then insert all source associations using `INSERT INTO site_jobs(site_id,job_id) SELECT site_id,? FROM site_jobs WHERE job_id=?`. The clone job and complete association set either commit together or roll back together. Do not overwrite any site's JSON/timestamps or replace a site's existing link set.
4. `saveJob` creates a fresh UUID and fresh timestamps and initializes runtime fields from the absent previous record (`server/store.mjs:162`, `:169`); its secret encoding reseals retained plaintext server-side (`:170`). No run/log/baseline rows are copied. Never call `updateJob` with the source id, `createRun`, `enqueue` or any archive-recovery import helper as part of cloning.
5. **No scheduler/watcher refresh is required for an always-paused new clone.** `scheduler.refresh` writes `nextRunAt` on every task (`server/scheduler.mjs:15`), which also rewrites existing tasks' `updatedAt` through `updateJob`. Avoid that side effect in this endpoint. Existing gates already prevent timers (`scheduler.mjs:16`) and watchers (`watcher.mjs:110`) on `enabled:false`. App should refresh its authoritative jobs **and sites** after the response so copied associations appear in both directions.

### Destination identities and ownership

- Original destination ids may be retained as configuration. They are unique **within** a job (`app.mjs:44`), not a database-global key. Retention first limits completed runs to `run.jobId===job.id` (`backup.mjs:424`), then checks destination id/remote/path (`:427`), and validates remote completion jobId/runId before removing current-format versions (`:445`). A fresh job with no copied runs has no right to prune its source job's history.
- Regenerating destination ids is also possible but is not necessary for ownership and changes more configuration. Do not copy old targets, run ids, local stage paths, remote completion records, `lastRun` or `archiveRecovery` metadata.
- Retaining a destination path does not create a new remote namespace. Existing `{datetime}` folders and task-based archive names remain the configured scheme; clone ids alone do not alter the physical destination path. Avoid widening this task into a retention/path-format redesign; test source-history isolation directly.

### Status/error boundaries

| Condition | Recommended response |
| --- | --- |
| Success, including queued/running non-system source | 201 public cloned job, paused, no run queued |
| Missing source job | 404 `JOB_NOT_FOUND` |
| Built-in/system task | 409 `SYSTEM_JOB_CLONE_FORBIDDEN` (specific stable code; deletion's 403 remains unchanged) |
| Invalid optional name/body or configuration | 400 through existing `VALIDATION_FAILED`/validation handling |
| Existing source outside roots/overlapping state/symlink | Existing 403 `SOURCE_PATH_FORBIDDEN` / `SOURCE_SYMLINK_FORBIDDEN` |
| Missing source file during ordinary create/enable validation | Existing 404 `SOURCE_PATH_MISSING`; a paused clone may retain an allowed missing source |
| Unauthenticated / missing CSRF or foreign Origin | Existing 401 / 403 via `app.mjs:110` |

The clone route must not reuse deletion's `JOB_BUSY` guard (`app.mjs:175`): configuration cloning does not operate on the original active run.
