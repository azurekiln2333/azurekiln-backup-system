# Backend research: site inventory and backup-job associations

Research date: 2026-10-24. Read-only source inspection; only this research file was written. This is a design recommendation, not an accepted product decision or implementation.

Planning review update: the user subsequently confirmed many-to-many associations in both directions. The consolidated `prd.md`, `design.md`, and `implement.md` are authoritative; historical cardinality alternatives below are superseded. The final plan also proposes all existing job types as eligible, multiple bare-host/HTTP(S) addresses, empty initial address/job lists, and tags without a separate category or notes field.

Decision update: the user subsequently explicitly confirmed many-to-many in both directions (several jobs per site and several sites per shared job). This supersedes all provisional single-owner alternatives/cardinality questions below. Remaining record/UX proposals are documented for final review in the task PRD/design.

## Existing contracts and extension points

- `shared/contracts.mjs:38` defines the existing job tag schema: up to 10 trimmed labels, each 1-32 characters, no comma/newline/NUL, deduplicated case-insensitively while retaining the first spelling. `jobSchema` starts at line 42; `settingsSchema` at line 131. There is no site entity, domain registry, site association, or general category table.
- `server/store.mjs:29` owns native SQLite state. Startup at line 43 uses additive `CREATE TABLE IF NOT EXISTS`, WAL, and `PRAGMA foreign_keys=ON`. Jobs/settings are JSON in SQL rows; IDs and job timestamps are generated by the store (`saveJob`, line 133). There is no migration framework or schema-version mechanism to extend for this feature.
- Public jobs are sanitized by `listJobs` / `getJob` at `server/store.mjs:126` / `:129`; old jobs default missing description/tags without changing existing rows. Only the store's explicitly private reads expose secret values. Site responses must not embed private job objects.
- `server/app.mjs:110` installs administrator authentication, origin, and CSRF middleware for all subsequent API endpoints. Existing collection/member CRUD conventions are `GET`, `POST` -> 201, `PATCH` -> authoritative saved object, and `DELETE` -> 204 (`:117-180`). `wrap` at line 15 handles async failures. Zod validation failures become structured 400 responses with field paths (`:306-312`). Unknown member IDs should follow the existing explicit 404 pattern rather than return an empty successful response.
- Jobs run independently of inventory metadata: job writes refresh scheduler/watchers (`server/app.mjs:118-180`); `server/store.mjs:184` creates run snapshots carrying `jobId`, name, and type. Site writes should not modify jobs, reset schedules, refresh watchers, enqueue work, or rewrite historical runs.
- `mergeConfig` at `server/store.mjs:19` recursively merges object patches while replacing arrays. Site PATCH can follow this convention: omitted arrays retain previous values; a supplied array replaces the full domain/tag/job set; an empty array clears it. Do not parse a partial site directly against defaults before merging, which could erase omitted fields.

## Smallest compatible model (provisional)

The pending user decision is whether a backup job can cover multiple sites. One site should be able to associate several existing jobs (for example files and a database). Do not encode a single `job.siteId` before that decision.

Recommended API shape:

```text
SiteInput {
  name: string,
  domains: string[],
  description: string,
  tags: string[],
  backupJobIds: string[]
}
Site = SiteInput + { id, createdAt, updatedAt }
```

- Keep site metadata separate from backup-task configuration. `backupJobIds` is an API projection of a single authoritative association set, not a second job record. Existing `GET /api/jobs` already supplies sanitized task details for joining in the frontend, so site APIs need no secret-bearing job payloads or duplicated status storage.
- Reuse the current tag validation by exporting a shared tag-list schema and consuming it in both `jobSchema` and a new `siteSchema`. Preserve all existing job tag behavior. Site tag values remain independent: binding or unbinding a job does not copy, add, or remove either object's tags.
- Tags already satisfy lightweight classification/filtering. A separate category taxonomy/table is unnecessary unless the user explicitly wants one exclusive category in addition to tags. An optional bounded free-text category is possible, but should not be introduced as an unconfirmed extra requirement.
- For persistence, add `sites(id TEXT PRIMARY KEY, data TEXT NOT NULL)` and `site_jobs(site_id TEXT REFERENCES sites(id) ON DELETE CASCADE, job_id TEXT REFERENCES jobs(id) ON DELETE CASCADE, PRIMARY KEY(site_id,job_id))`. Keep site JSON limited to metadata/timestamps; project `backupJobIds` from the relation table. Add a `job_id` index for reverse lookups/deletion.
- This is the smallest model with referential integrity using infrastructure already enabled by the store. It does not require rewriting old job JSON, adding a mandatory site field, or changing scheduler/executor contracts. A site containing `backupJobIds` only inside JSON would use one fewer table but require manual referential validation and transactional cleanup in every job deletion path.
- If the user chooses one site per job, add `UNIQUE(job_id)` to the relation table and return a useful 409 conflict identifying the owning site. If shared associations are allowed, omit that constraint. There must be only one authoritative relation, not both `sites.jobIds` and `jobs.siteIds` persisted independently.
- `POST /api/sites`, `GET /api/sites`, `GET /api/sites/:id`, `PATCH /api/sites/:id`, `DELETE /api/sites/:id` follow current route conventions. Basic collection search/filtering can remain frontend-side while the inventory is small, matching current all-jobs retrieval; adding pagination is not necessary for this request.

## Validation and product decisions to settle

- Site names should use existing human-label conventions (trimmed, required, bounded); IDs/timestamps are server-owned. Reasonable defaults are the existing name limit of 100 characters and description limit of 500, but the PRD should approve those limits.
- Decide whether a site may exist before a domain or backup job is configured. Supporting `domains: []` and `backupJobIds: []` is operationally useful and keeps record creation independent of backup creation.
- Decide whether domain entries are hostnames only or HTTP(S) URLs with scheme/port/path. Hostname-only storage is simplest; validate and normalize deterministically (case, trailing dot, internationalized names) without DNS/network requests. Deduplicate within the site. Do not assume domains are globally unique across sites without a requirement: path-based applications and shared frontends can reuse a host.
- Validate all supplied job IDs before writing any site changes. Reject nonexistent IDs with a stable application error and preserve previous state. Deduplicate IDs or reject duplicate IDs consistently; the relation primary key remains the storage backstop.
- Decide whether the global built-in `system-config` job is selectable. Excluding it is a useful default because it describes this backup application's state rather than one site's payload; however, this is a product choice. Normal directory, Vaultwarden, and newapi tasks can remain eligible without checking source accessibility or requiring a completed backup.
- A binding is metadata only. It must not assert that a job necessarily captures the full site, execute probes, infer paths from domains, or alter encrypted credentials.

## Migration, transactions, and deletion invariants

1. Startup must add the new table(s) idempotently. On a pre-feature database, `GET /api/sites` returns `[]`; every legacy job and old JSON shape stays usable. Reopening an already-upgraded database must preserve site IDs, metadata, and exact associations.
2. Use a single SQLite transaction for site metadata plus its replacement relation set. If any bound job is invalid or uniqueness is violated, no partial site update or removed prior association survives. Keep transaction ownership in the store; do not build multi-write correctness out of route-level loops.
3. Deleting a site deletes only its metadata and relation rows. It must leave jobs, their enabled state/schedule, watch baselines, historical runs/logs, local archives, and remote archives unchanged. It need not reject an active job because execution is independent of the metadata.
4. Deleting a job detaches it from every site and retains each site's other metadata/associations. The existing route rejects queued/running jobs (`server/app.mjs:175`) and protects `system-config` (`:174`); preserve those behaviors. Store deletion at `server/store.mjs:154` currently removes the watch baseline and job but deliberately does not delete runs/logs or remote archives. `ON DELETE CASCADE` on the join provides link cleanup without expanding that deletion scope.
5. Unbinding is relation-only. Never infer deletion authorization from site ownership or domain names. Existing archive ownership and retention rules continue to use job/destination IDs.
6. Derive both directions from current links. Site detail may join `backupJobIds` to sanitized jobs; a jobs-page site badge/filter, if required, should use the same association source. Historical runs do not need a site snapshot for the requested inventory page.
7. Do not automatically migrate existing job tags into sites, infer site records from task names, or alter task source paths. Such heuristics would create unconfirmed records and associations.

## System-configuration backup and restore

- `server/backup.mjs:242-286` creates an online snapshot of the entire `state.sqlite`, switches only the completed snapshot to DELETE journaling, checks integrity, and includes it with the encryption key and rclone configuration. Site/relation tables inside this database are included automatically; do not add separate `sites.json` files or duplicate data in the archive manifest.
- `server/system-restore.mjs:11-12` defines archive files, and `:28-61` validates hashes, SQLite integrity, and the key marker. This validation does not whitelist application SQL tables. Adding site tables does not require changing the `system.json` format version or required file list.
- Restore replaces the whole state database, preserving prior files for rollback (`server/system-restore.mjs:130-210`). It is a restore of the archived inventory, not a merge with current live sites/jobs. The UI should continue to use existing restart-based restore behavior.
- `createApp` applies the pending database before `createStore` (`server/app.mjs:73-85`). Therefore importing an older archive with no sites tables naturally runs the additive table creation next, yielding an empty inventory. Importing a current archive restores the stored IDs and associations alongside their jobs.
- If foreign-key relations are chosen, include a `PRAGMA foreign_key_check` assertion in persistence/restore tests. Existing `PRAGMA integrity_check` alone is not a referential-integrity assertion. Do not require site tables during archive pre-validation, which would break old archives.

- `tests/api.test.mjs:20` — reusable authenticated isolated fixture. Add CRUD/validation/auth/CSRF/reverse-link/deletion regression coverage, using existing `inputJob` at line 65. Existing tags regression at line 168 must continue passing.
- A focused new `tests/sites.test.mjs` is reasonable for store restart, additive legacy migration, exact binding-set persistence, transaction rollback, shared/single-owner semantics, and SQL referential integrity, without external tooling. Public API coverage can remain in `tests/api.test.mjs` to reuse its fixture.
- `tests/executor.test.mjs:78` currently covers reconciliation of imported archive metadata, not a full system-inventory restore. Add a meaningful system snapshot/restore test proving site IDs, tags/domains, and associations survive the real existing restore path; include an old-format archive/database case. This can use the existing real archive tools when the full lifecycle is exercised.
- `.trellis/spec/backend/backup-lifecycle.md` — record site persistence, association ownership, deletion, and old-archive compatibility after implementation is verified.

No production edits are inherently required in `server/backup.mjs`, `server/system-restore.mjs`, scheduler, watcher, or the newapi adapter if all new state lives in `state.sqlite`. Read their behavior for compatibility and test it; avoid unrelated backup fixes in this site task.

Recommended acceptance checks: unauthenticated sites read returns 401; mutations without CSRF return 403; empty/new inventory; create/edit/reload; missing member 404; invalid domain/tag/job link leaves prior values intact; site deletion preserves all jobs and runs; job deletion cleans all links; bindings to paused/source-offline jobs remain manageable; old DB and old archive upgrade; current archive restores all relations; public payloads contain no archive/database/rclone passwords. Run the project's standard `npm test`, `npm run check`, `npm run build`, then relevant real browser/layout checks once implementation exists. No tests were run during this source-only research.

## Review of the consolidated plan

Reviewed the current PRD/design/execution plan and implement/check manifests after many-to-many confirmation. No blocking persistence/API/restore contradictions found. The authoritative relation, cascade-only deletion, atomic PATCH replacement, old-database creation, whole-state restore, public DTO boundary, and existing task protections are consistent with the current implementation.

Before the frontend/backend parallel stage, the shared-contract checkpoint should fix the address count/length constants, the exact canonical bare-host representation (including default scheme for link generation), URL path case preservation, and duplicate rules. The design deliberately delegates these routine details to that checkpoint; they are not another product-cardinality question. Use the same exported normalized-address/link contract in API validation and UI, then keep tests pinned to that behavior.

For implementation precision, specify whether site `updatedAt` means explicit site saves only or also job-deletion-induced unlinking. FK cascade does not update site JSON timestamps automatically. Either documented behavior is compatible with the approved inventory requirements, provided the UI reloads authoritative associations after job deletion and does not rely on timestamps alone to invalidate relation data.
